## 第一节 为什么需要架构

- 没有架构的代码长什么样

---

### "上帝 Activity"

```kotlin
class MainActivity : ComponentActivity() {
    override fun onCreate(savedInstanceState: Bundle?) {
        setContent {
            var list by remember { mutableStateOf(emptyList<Item>()) }
            LaunchedEffect(Unit) {
                val db = Room.databaseBuilder(...).build()          // 直接建数据库
                val response = OkHttpClient().newCall(...).execute() // 直接发网络请求
                val json = JSONObject(response.body!!.string())      // 直接解析
                list = parse(json)
            }
            LazyColumn { items(list) { ItemRow(it) } }
        }
    }
}
```

问题：无法测试、无法复用、改一处牵一片、旋转屏幕重新请求。

---

### 架构的两条核心原则

**1. 分离关注点（Separation of Concerns）**

- UI 组件只负责显示，不承载业务逻辑
- 数据获取、缓存、转换在各自的层里完成

**2. 数据驱动 UI（Drive UI from data models）**

- UI 是数据模型的**函数**
- 数据模型独立于 UI 组件的生命周期

---

### 常见架构模式对比

| 模式 | 表现层 | 特点 |
| --- | --- | --- |
| MVC | Controller | Android 中 Activity 既是 V 又是 C，职责混乱 |
| MVP | Presenter | 需要写大量接口，Presenter 易膨胀 |
| **MVVM** | ViewModel | 官方推荐，配合数据绑定/Compose 最自然 |
| MVI | Intent + State | 单一状态、单向数据流，适合复杂交互 |

> Compose + ViewModel + StateFlow 实际上已经融合了 MVVM 与 MVI 的思想。

## 第二节 推荐的应用架构

- 三层结构
- 依赖方向
- 数据流向

---

### 官方推荐的三层架构

```text
┌──────────────────────────────────────────────┐
│  UI 层    Composable  ←→  ViewModel           │
│           （显示状态）      （持有 UI 状态）      │
└──────────────────────┬───────────────────────┘
                       ↓ 依赖
┌──────────────────────────────────────────────┐
│  Domain 层（可选）  UseCase                    │
│           （封装复杂业务规则、复用逻辑）          │
└──────────────────────┬───────────────────────┘
                       ↓ 依赖
┌──────────────────────────────────────────────┐
│  数据层   Repository  →  DataSource            │
│                        （网络 / 本地数据库）     │
└──────────────────────────────────────────────┘
```

**依赖方向单向向下**，下层永远不知道上层的存在。

---

### 各层的职责

| 层 | 组成 | 职责 | 不该做的事 |
| --- | --- | --- | --- |
| UI | Composable | 渲染状态、上报事件 | 业务逻辑、数据获取 |
| UI | ViewModel | 持有 UI 状态、处理事件 | 持有 View/Context 引用 |
| Domain | UseCase | 封装可复用的业务规则 | 直接访问网络/数据库 |
| Data | Repository | 决定数据来源、缓存策略 | 依赖 Android UI 类 |
| Data | DataSource | 具体的网络/数据库访问 | 业务判断 |

---

### 一个完整的数据流

```text
用户点击"刷新"
    ↓ 事件
Composable → viewModel.onRefresh()
    ↓
ViewModel → repository.refresh()
    ↓
Repository → api.getNews()  →  dao.insertAll()
    ↓
dao.observeAll(): Flow  ────────────┐
    ↓                               │
Repository.observeNews(): Flow      │  数据变化自动推送
    ↓                               │
ViewModel.uiState: StateFlow ───────┘
    ↓ 状态
Composable 重组，显示新数据
```

## 第三节 UI 层与 MVVM

- UI State 建模

---

### UI State 建模

```kotlin
data class NewsUiState(
    val articles: List<Article> = emptyList(),
    val isLoading: Boolean = false,
    val isRefreshing: Boolean = false,
    val error: String? = null,
    val selectedCategory: Category = Category.ALL
) {
    val isEmpty: Boolean get() = articles.isEmpty() && !isLoading
}
```

原则：

- **一个屏幕一个 UI State 类**，不可变（`data class` + `copy`）
- 派生数据用**计算属性**，不要存冗余字段
- 不要把 `Composable` 或 `Context` 放进 State

---

### ViewModel 实现

```kotlin
class NewsViewModel(
    private val repository: NewsRepository
) : ViewModel() {

    private val _uiState = MutableStateFlow(NewsUiState(isLoading = true))
    val uiState: StateFlow<NewsUiState> = _uiState.asStateFlow()

    init { observeNews(); refresh() }

    private fun observeNews() = viewModelScope.launch {
        repository.observeNews().collect { list ->
            _uiState.update { it.copy(articles = list, isLoading = false) }
        }
    }

    fun refresh() = viewModelScope.launch {
        _uiState.update { it.copy(isRefreshing = true) }
        val r = repository.refresh()
        _uiState.update {
            it.copy(isRefreshing = false, error = (r as? NetworkResult.Error)?.message)
        }
    }
}
```

---

### UI 层拆分：Route 与 Screen

```kotlin
// 有状态：连接 ViewModel，负责收集状态
@Composable
fun NewsRoute(viewModel: NewsViewModel = viewModel()) {
    val uiState by viewModel.uiState.collectAsStateWithLifecycle()
    NewsScreen(
        uiState = uiState,
        onRefresh = viewModel::refresh,
        onArticleClick = viewModel::onArticleClick
    )
}

// 无状态：纯 UI，可预览、可测试
@Composable
fun NewsScreen(
    uiState: NewsUiState,
    onRefresh: () -> Unit,
    onArticleClick: (Long) -> Unit
) { /* ... */ }
```

> 这种"Route + Screen"的拆法能让每个界面都被 `@Preview` 直接预览。

### ViewModel 的常见错误

```kotlin
class BadViewModel(
    private val context: Context,          // ✗ 持有 Activity Context → 内存泄漏
    private val textView: TextView         // ✗ 持有 View
) : ViewModel() {

    fun load() {
        GlobalScope.launch { }              // ✗ 不受生命周期约束
        Toast.makeText(context, ...)        // ✗ ViewModel 不该直接操作 UI
    }
}
```

正确做法：需要 Context 时用 `AndroidViewModel(application)` 或注入 `@ApplicationContext`；需要提示时发送**事件**给 UI。

## 第四节 数据层与 Repository

### Repository 的职责

```kotlin
interface NewsRepository {
    fun observeNews(): Flow<List<Article>>
    suspend fun refresh(): NetworkResult<Unit>
    suspend fun toggleFavorite(id: Long)
}

class DefaultNewsRepository(
    private val remote: NewsRemoteDataSource,
    private val local: NewsLocalDataSource,
    private val dispatcher: CoroutineDispatcher = Dispatchers.IO
) : NewsRepository {

    override fun observeNews(): Flow<List<Article>> =
        local.observeAll().map { list -> list.map { it.toDomain() } }

    override suspend fun refresh(): NetworkResult<Unit> = withContext(dispatcher) {
        safeApiCall {
            val remoteList = remote.fetchNews()
            local.replaceAll(remoteList.map { it.toEntity() })
        }
    }
}
```

---

### 面向接口带来的可测试性

```kotlin
// 测试用的假实现，无需网络和数据库
class FakeNewsRepository : NewsRepository {
    private val flow = MutableStateFlow(listOf(Article(1, "测试标题")))
    override fun observeNews() = flow
    override suspend fun refresh() = NetworkResult.Success(Unit)
    override suspend fun toggleFavorite(id: Long) {}
}

@Test
fun `刷新失败时显示错误信息`() = runTest {
    val vm = NewsViewModel(FakeNewsRepository(shouldFail = true))
    vm.refresh()
    assertEquals("网络连接失败", vm.uiState.value.error)
}
```

> Repository 用接口声明，是"可测试架构"的关键一步。

---

### UseCase（可选层）

```kotlin
class GetRecommendedArticlesUseCase(
    private val newsRepo: NewsRepository,
    private val userRepo: UserRepository
) {
    operator fun invoke(): Flow<List<Article>> =
        combine(newsRepo.observeNews(), userRepo.observeInterests()) { news, interests ->
            news.filter { it.tags.any(interests::contains) }
                .sortedByDescending { it.publishedAt }
        }
}

// 使用：像调用函数一样
val recommended = getRecommendedArticles()
```

何时引入 UseCase：

- 逻辑需要**跨多个 Repository**
- 同一段业务逻辑被**多个 ViewModel** 复用
- ViewModel 已经变得臃肿

### 依赖注入解决什么问题

```kotlin
// ✗ 自己创建依赖：耦合死，无法替换，无法测试
class NewsViewModel : ViewModel() {
    private val repo = DefaultNewsRepository(
        NewsRemoteDataSource(Retrofit.Builder()...build()),
        NewsLocalDataSource(Room.databaseBuilder(...).build())
    )
}

// ✓ 依赖由外部传入
class NewsViewModel(private val repo: NewsRepository) : ViewModel()
```

> 依赖注入 = **把"创建依赖"的职责移出使用方**。

---

### 手动依赖注入

```kotlin
// 应用级容器
class AppContainer(context: Context) {
    private val db by lazy { AppDatabase.getInstance(context) }
    private val api by lazy { NetworkModule.api }

    val newsRepository: NewsRepository by lazy {
        DefaultNewsRepository(NewsRemoteDataSource(api), NewsLocalDataSource(db.newsDao()))
    }
}

class MyApplication : Application() {
    lateinit var container: AppContainer
    override fun onCreate() { super.onCreate(); container = AppContainer(this) }
}
```

> 小项目手动注入足够清晰，本课程的实验可以先用这种方式。

### 提供依赖

```kotlin
@Module
@InstallIn(SingletonComponent::class)
object DataModule {

    @Provides @Singleton
    fun provideDatabase(@ApplicationContext ctx: Context): AppDatabase =
        Room.databaseBuilder(ctx, AppDatabase::class.java, "app.db").build()

    @Provides
    fun provideNewsDao(db: AppDatabase): NewsDao = db.newsDao()

    @Provides @Singleton
    fun provideApi(): NewsApi = NetworkModule.api
}

@Module
@InstallIn(SingletonComponent::class)
abstract class RepositoryModule {
    @Binds
    abstract fun bindNewsRepository(impl: DefaultNewsRepository): NewsRepository
}
```

### 注入到 ViewModel

```kotlin
@HiltViewModel
class NewsViewModel @Inject constructor(
    private val repository: NewsRepository,
    savedStateHandle: SavedStateHandle
) : ViewModel() { /* ... */ }
```

```kotlin
@Composable
fun NewsRoute(viewModel: NewsViewModel = hiltViewModel()) {
    val uiState by viewModel.uiState.collectAsStateWithLifecycle()
    NewsScreen(uiState, viewModel::refresh)
}
```

> Hilt 在编译期生成依赖图，缺依赖时**编译报错**而不是运行时崩溃。

---

### Hilt 作用域

| 注解 | 生命周期 |
| --- | --- |
| `@Singleton` | 整个应用 |
| `@ActivityRetainedScoped` | 跨配置变更存活（与 ViewModel 同寿命） |
| `@ActivityScoped` | 单个 Activity |
| `@ViewModelScoped` | 单个 ViewModel |

> 作用域用错会导致内存泄漏或对象被意外共享，默认**不加作用域**（每次注入新实例）最安全。

### 单模块的包结构

```text
com.example.newsapp/
├── data/
│   ├── local/       Room：Entity、Dao、Database
│   ├── remote/      Retrofit：Api、Dto
│   ├── repository/  Repository 实现
│   └── mapper/      DTO/Entity ↔ Domain 映射
├── domain/
│   ├── model/       领域模型
│   ├── repository/  Repository 接口
│   └── usecase/
├── ui/
│   ├── news/        NewsRoute、NewsScreen、NewsViewModel、NewsUiState
│   ├── detail/
│   ├── component/   可复用组件
│   ├── navigation/
│   └── theme/
└── di/              依赖注入模块
```

---

### 按功能分包 vs 按层分包

```text
按层（layer）：              按功能（feature）：
data/                       news/
  ├─ NewsDao                  ├─ NewsScreen
  ├─ ArticleDao               ├─ NewsViewModel
ui/                           └─ NewsRepository
  ├─ NewsScreen             profile/
  ├─ ProfileScreen            ├─ ProfileScreen
                              └─ ProfileViewModel
```

> **小项目按层，中大型项目按功能**。按功能分包时，一个需求的改动集中在一个目录内。

---

### 多模块

```text
:app                  应用壳，负责组装
:feature:news         新闻功能模块
:feature:profile      个人中心模块
:core:data            数据层
:core:database        Room
:core:network         网络
:core:designsystem    主题与通用组件
:core:common          工具类
```

好处：**编译加速**（只重编改动的模块）、依赖边界清晰、便于团队并行开发。
代价：配置复杂度上升，小项目不必上来就拆。

## 本章小结

- 架构的目的：**分离关注点** + **数据驱动 UI**，让改动成本可控
- 三层：UI（Composable + ViewModel）、Domain（UseCase，可选）、Data（Repository + DataSource）
- 依赖方向单向向下；Repository 用接口声明以便替换与测试
- UI 层拆成有状态的 Route 与无状态的 Screen
- 依赖注入把"创建依赖"移出使用方；小项目手动容器，大项目用 Hilt
